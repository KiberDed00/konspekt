## 0 Зачем нужны принципы

Разработка ПО — это не только написание кода, который «работает сейчас». Важно, чтобы код:

- ✅ работал корректно;
- ✅ был понятен другим разработчикам;
- ✅ легко тестировался;
- ✅ легко изменялся;
- ✅ не ломался при добавлении новой функциональности;
- ✅ мог поддерживаться годами.

> 💡 **Главная проблема** — сложность. Чем больше система, тем дороже каждое изменение.

Принципы разработки помогают:

1. 🧩 **Управлять сложностью** — разбивать систему на понятные части.
2. 💰 **Снижать стоимость изменений** — делать код гибким.
3. 🗣️ **Улучшать коммуникацию** — давать команде общий язык.
4. 🏆 **Повышать качество** — уменьшать количество ошибок.
5. 🛠️ **Облегчать сопровождение** — чтобы новый разработчик мог быстро разобраться.

**Уровни действия принципов:**

## 1 Базовые принципы проектирования

### 1-1 Модульность

> **Модульность** — разбиение системы на относительно независимые части, каждая из которых выполняет свою задачу.

**Признаки хорошей модульности:**

- 🎯 у модуля чёткая зона ответственности;
- 🔒 модуль скрывает внутреннюю реализацию;
- 🔌 взаимодействие через понятный интерфейс;
- 🔄 модуль можно заменить без переписывания системы.

**Пример:** интернет-магазин можно разделить на модули:

```text
┌──────────┬──────────┬──────────┬──────────┐
│ Каталог  │ Корзина  │  Заказы  │  Оплата  │
├──────────┼──────────┼──────────┼──────────┤
│ Доставка │ Уведомл. │  Склад   │  Отчёты  │
└──────────┴──────────┴──────────┴──────────┘
```

| Плюсы | Минусы |
|---|---|
| ✅ Проще тестировать | ❌ Нужно проектировать интерфейсы |
| ✅ Проще переиспользовать | ❌ Сложнее интеграция |
| ✅ Проще делить работу | ❌ Неверное разбиение усложняет систему |
| ✅ Меньше связности | |

---

### 1-2 Абстракция

> **Абстракция** — выделение существенных характеристик объекта и скрытие несущественных деталей.

**Пример:**

- Вместо `ArrayList` → интерфейс `List`
- Вместо `MySQLUserRepository` → `UserRepository`

**Зачем:**

- 🔗 уменьшается связанность;
- 🔄 можно менять реализацию;
- 🧪 проще тестировать (mock-объекты).

> ⚠️ **Осторожно:** абстракция не должна быть «дырявой». Если для работы с ней нужно знать детали реализации — это плохая абстракция.

---

### 1-3 Инкапсуляция

> **Инкапсуляция** — скрытие внутреннего состояния объекта и доступ через публичный интерфейс.

**Что даёт:**

- 🛡️ защита инвариантов класса;
- 🎛️ контроль изменений состояния;
- 🔗 уменьшение связанности;
- 🔄 возможность менять реализацию.

**Пример:**

```java
class BankAccount {
    private Money balance;

    public void deposit(Money amount) {
        if (amount.isNegative()) {
            throw new IllegalArgumentException("Сумма должна быть положительной");
        }
        balance = balance.add(amount);
    }

    public Money getBalance() {
        return balance;
    }
}
```

> ❌ **Типичная ошибка:** делать все поля публичными или генерировать getters/setters для всего подряд. Это не инкапсуляция, а формальный доступ.

---

### 1-4 Разделение ответственности

> **Separation of Concerns (SoC)** — система должна быть разделена на части, каждая из которых отвечает за свою задачу.

**Примеры:**

- UI не содержит бизнес-логику;
- бизнес-логика не знает про БД;
- доступ к данным не форматирует ответ.

**Проявления SoC:**

- MVC, MVP, MVVM;
- слоистая архитектура;
- Clean Architecture;
- Hexagonal Architecture;
- микросервисы.

---

### 1-5 Слабая связанность и высокая связность

Два взаимодополняющих принципа.

| Принцип | Суть |
|---|---|
| **Low Coupling** (слабая связанность) | Модули минимально зависят друг от друга |
| **High Cohesion** (высокая связность) | Элементы внутри модуля тесно связаны одной задачей |

**Идеал:** модули слабо связаны между собой, но внутри каждого — сильная связность.

---

### 1-6 Повторное использование

> **Повторное использование** — применение существующих решений в новых контекстах.

> ⚠️ **Не обобщай раньше времени.**

**Правило трёх:**

1. Первый раз — просто пишем код.
2. Второй раз — терпим дублирование.
3. Третий раз — задумываемся об абстракции.

## 2 Принципы написания кода

### 2-1 DRY

> **DRY — Don't Repeat Yourself** — не повторяй себя. Каждое знание имеет единственное представление.

**Что считается дублированием:**

- копипаста кода;
- дублирование бизнес-правил;
- дублирование конфигурации;
- дублирование структуры данных.

**Почему это плохо:**

- ❌ при изменении нужно править в нескольких местах;
- ❌ легко забыть одно из мест;
- ❌ растёт риск ошибок.

> 💡 **Важно:** DRY ≠ «объединить любой похожий код». Если код меняется по разным причинам — не объединяй.

---

### 2-2 KISS

> **KISS — Keep It Simple, Stupid** — делай проще. Простое решение обычно лучше сложного.

**Признаки простого кода:**

- 📖 легко читается;
- 🧪 легко тестируется;
- 🧩 минимум абстракций;
- ⏱️ не требует долгого изучения.

**Что мешает простоте:**

- преждевременная оптимизация;
- избыточные паттерны;
- сложные иерархии наследования;
- «умный» код без комментариев.

---

### 2-3 YAGNI

> **YAGNI — You Aren't Gonna Need It** — не реализуй то, что может понадобиться в будущем.

**Проблема:** разработчики добавляют функциональность «на всякий случай». В итоге:

- код усложняется;
- появляются неиспользуемые ветки;
- растёт стоимость поддержки.

**Правильно:** реализуем только то, что нужно сейчас.

---

### 2-4 SOLID

> Пять принципов объектно-ориентированного проектирования.

| Принцип | Расшифровка | Суть |
|:---:|---|---|
| **S** | Single Responsibility | У класса одна причина для изменения |
| **O** | Open Closed | Открыт для расширения, закрыт для изменения |
| **L** | Liskov Substitution | Наследник заменяет родителя без поломки логики |
| **I** | Interface Segregation | Много специализированных интерфейсов лучше одного общего |
| **D** | Dependency Inversion | Зависимость от абстракций, а не от реализаций |

#### S Single Responsibility Principle

> Класс должен иметь только одну причину для изменения.

<table>
<tr><th>❌ Плохо</th><th>✅ Хорошо</th></tr>
<tr>
<td>

```java
class Order {
    void calculateTotal() { }
    void saveToDatabase() { }
    void printInvoice() { }
}
```

</td>
<td>

```java
class Order { }
class OrderRepository { }
class InvoicePrinter { }
```

</td>
</tr>
</table>

---

#### O Open Closed Principle

> Класс открыт для расширения, закрыт для изменения.

<table>
<tr><th>❌ Плохо</th><th>✅ Хорошо</th></tr>
<tr>
<td>

```java
if (type == "card") { }
else if (type == "cash") { }
else if (type == "crypto") { }
```

</td>
<td>

```java
interface PaymentMethod {
    void pay();
}

class CardPayment implements PaymentMethod { }
class CashPayment implements PaymentMethod { }
```

</td>
</tr>
</table>

---

#### L Liskov Substitution Principle

> Объекты наследника должны заменять объекты родителя без нарушения корректности.

**Классический пример:** квадрат и прямоугольник. Если `Square` наследует `Rectangle`, но меняет поведение сеттеров — нарушение LSP.

**Признаки нарушения:**

- наследник выбрасывает исключение там, где родитель работает;
- игнорирует часть поведения родителя;
- клиентский код проверяет тип наследника.

---

#### I Interface Segregation Principle

> Клиенты не должны зависеть от методов, которые они не используют.

<table>
<tr><th>❌ Плохо</th><th>✅ Хорошо</th></tr>
<tr>
<td>

```java
interface Worker {
    void work();
    void eat();
    void sleep();
}
```

</td>
<td>

```java
interface Workable { void work(); }
interface Eatable { void eat(); }
interface Sleepable { void sleep(); }
```

</td>
</tr>
</table>

---

#### D Dependency Inversion Principle

> Модули верхнего уровня не должны зависеть от модулей нижнего уровня.

<table>
<tr><th>❌ Плохо</th><th>✅ Хорошо</th></tr>
<tr>
<td>

```java
class OrderService {
    private MySQLOrderRepository repository 
        = new MySQLOrderRepository();
}
```

</td>
<td>

```java
class OrderService {
    private final OrderRepository repository;

    OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}
```

</td>
</tr>
</table>

---

### 2-5 Композиция вместо наследования

> Наследование создаёт жёсткую связь. Композиция — более гибкий подход.

<table>
<tr><th>❌ Плохо</th><th>✅ Хорошо</th></tr>
<tr>
<td>

```java
class Car extends Engine { }
```

</td>
<td>

```java
class Car {
    private Engine engine;
}
```

</td>
</tr>
</table>

**Почему композиция лучше:**

- 🔗 меньше связанность;
- 🔄 проще менять поведение;
- 🛡️ нет хрупкого базового класса;
- 🧩 можно комбинировать поведение.

---

### 2-6 Закон Деметры

> **Law of Demeter** — объект должен знать как можно меньше о других объектах.

<table>
<tr><th>❌ Плохо</th><th>✅ Хорошо</th></tr>
<tr>
<td>

```java
order.getCustomer()
     .getAddress()
     .getCity()
     .getName();
```

</td>
<td>

```java
order.getCustomerCity();
```

</td>
</tr>
</table>

**Суть:** не вызывай методы у объектов, полученных через цепочку.

---

### 2-7 Fail Fast

> Ошибка должна обнаруживаться как можно раньше.

**Практики:**

- проверять входные данные;
- использовать assertions;
- выбрасывать исключения при некорректном состоянии;
- не скрывать ошибки.

```java
public void setAge(int age) {
    if (age < 0) {
        throw new IllegalArgumentException("Возраст не может быть отрицательным");
    }
    this.age = age;
}
```

---

### 2-8 Защитное программирование

> Код должен корректно реагировать на некорректные данные.

**Что входит:**

- ✅ валидация входных данных;
- ✅ обработка исключений;
- ✅ проверка граничных условий;
- ✅ понятные сообщения об ошибках;
- ✅ логирование.

> ⚠️ Не путать с избыточной проверкой всего подряд.

---

### 2-9 Читаемость и единообразие

> Код читается гораздо чаще, чем пишется.

**Принципы:**

- понятные имена;
- единый стиль;
- небольшие функции;
- минимум комментариев;
- без «магических чисел»;
- последовательная структура проекта.

<table>
<tr><th>❌ Плохо</th><th>✅ Хорошо</th></tr>
<tr>
<td>

```java
int d;
```

</td>
<td>

```java
int daysUntilDeadline;
```

</td>
</tr>
</table>

---

### 2-10 Принцип наименьшего удивления

> Поведение кода должно быть предсказуемым.

- метод `save()` сохраняет, а не удаляет;
- `getBalance()` не меняет баланс;
- названия соответствуют действию.

## 3 Процессные принципы

### 3-1 Итеративная разработка

> Разработка идёт короткими итерациями.

**Плюсы:**

- ⚡ быстрая обратная связь;
- 🐛 раннее обнаружение ошибок;
- 🔄 уточнение требований по ходу;
- 🎯 снижение риска сделать не то.

**Пример:** MVP — минимально жизнеспособный продукт.

---

### 3-2 Agile подходы

> Agile — набор ценностей и принципов.

**Основные идеи:**

- 👥 люди и взаимодействие важнее процессов и инструментов;
- 🚀 работающий продукт важнее документации;
- 🤝 сотрудничество с заказчиком важнее контракта;
- 🔄 готовность к изменениям важнее плана.

**Фреймворки:** Scrum · Kanban · XP

---

### 3-3 Версионирование

> Использование систем контроля версий (чаще всего Git).

**Практики:**

- атомарные коммиты;
- понятные сообщения;
- ветвление;
- code review;
- pull request;
- trunk-based development / Git Flow.

**Семантическое версионирование:**

| Часть | Значение |
|---|---|
| `MAJOR` | Несовместимые изменения |
| `MINOR` | Новая функциональность |
| `PATCH` | Исправления |

---

### 3-4 Code Review

> Проверка кода другими разработчиками.

**Цели:**

- 🔍 найти ошибки;
- 📈 улучшить качество;
- 🧠 распространить знания;
- 📏 соблюсти стандарты;
- 🏛️ обсудить архитектурные решения.

**Хорошие практики:**

- небольшие PR;
- понятное описание;
- конструктивная обратная связь;
- авто-проверки до review.

---

### 3-5 Тестирование

**Пирамида тестирования:**

```text
        ▲
       ╱ ╲        E2E — мало, медленные
      ╱───╲
     ╱     ╲      Интеграционные — меньше, медленнее
    ╱───────╲
   ╱         ╲    Модульные — много, быстрые
  ╱───────────╲
```

**Виды тестов:** unit · integration · functional · regression · performance · security

**TDD — Test Driven Development:**

1. 🔴 Пишем падающий тест.
2. 🟢 Пишем минимальный код, чтобы тест прошёл.
3. 🔵 Рефакторим.

---

### 3-6 CI CD

| Аббревиатура | Расшифровка | Что даёт |
|---|---|---|
| **CI** | Continuous Integration | Изменения часто сливаются и автоматически проверяются |
| **CD** | Continuous Delivery / Deployment | Непрерывная доставка или развёртывание |

**Типичный pipeline:**

```text
Сборка → Линтеры → Тесты → Сканирование → Артефакт → Staging → Production
```

**Плюсы:**

- ⚡ быстрая обратная связь;
- 🛡️ меньше ручных ошибок;
- 🚀 предсказуемые релизы.

---

### 3-7 Рефакторинг

> **Рефакторинг** — улучшение структуры кода без изменения поведения.

**Когда нужен:**

- код трудно читать;
- появилось дублирование;
- методы слишком длинные;
- классы делают слишком много;
- перед добавлением функциональности.

> 🛡️ Лучше делать его под защитой тестов.

---

### 3-8 Документация

> Документация должна быть полезной, а не формальной.

**Виды:**

- 📄 README — как запустить проект;
- 🔌 API-документация;
- 🏛️ архитектурные решения — ADR;
- 📊 схемы;
- 💬 комментарии в коде.

> 💡 Комментарий должен объяснять **«почему»**, а не **«что»**.

---

### 3-9 Управление техническим долгом

> **Технический долг** — накопленные компромиссы, усложняющие разработку.

**Примеры:** костыли · устаревшие библиотеки · отсутствие тестов · плохая архитектура · дублирование.

**Что делать:**

- 📝 фиксировать долг;
- 📊 оценивать влияние;
- 📅 планировать погашение;
- 🚫 не допускать бесконтрольного накопления.

**Квадранты технического долга:**

|  | Необходимый | Ненужный |
|---|---|---|
| **Осознанный** | ✅ Оправдан | ⚠️ Риск |
| **Неосознанный** | 😕 Опасно | ❌ Критично |

## 4 Архитектурные принципы

### 4-1 Разделение на слои

**Типичные слои:**

```text
┌──────────────────────┐
│   Представление      │  ← UI / API
├──────────────────────┤
│   Приложение         │  ← use cases
├──────────────────────┤
│   Домен              │  ← бизнес-логика
├──────────────────────┤
│   Инфраструктура     │  ← БД, внешние сервисы
└──────────────────────┘
```

> 📐 **Правило зависимостей:** зависимости направлены внутрь, к домену. Домен не знает о БД, фреймворке или UI.

---

### 4-2 Clean Architecture

> Бизнес-логика не зависит от фреймворков, БД, UI и внешних сервисов.

**Слои:**

1. Entities
2. Use Cases
3. Interface Adapters
4. Frameworks & Drivers

**Плюсы:** 🧪 тестируемость · 🔌 независимость от технологий · 🔄 гибкость

---

### 4-3 Hexagonal Architecture

> Также известна как **Ports and Adapters**.

- 🎯 Ядро приложения
- 🔌 Порты — интерфейсы
- 🔧 Адаптеры — реализации для БД, HTTP, очередей

---

### 4-4 DDD Domain Driven Design

**Ключевые идеи:**

- 🗣️ единый язык — ubiquitous language;
- 🎯 ограниченные контексты — bounded contexts;
- 🧱 сущности;
- 💎 value objects;
- 📦 агрегаты;
- 📡 доменные события.

> DDD помогает бороться со сложностью предметной области.

---

### 4-5 API first и контракты

> Сначала проектируем API, потом реализацию.

**Плюсы:**

- 👥 команды работают параллельно;
- 📄 контракт понятен заранее;
- 🔗 меньше интеграционных проблем.

## 5 Нефункциональные аспекты

> Принципы касаются не только кода, но и качества системы.

- 🛡️ защита от OWASP Top 10;
- 🔒 шифрование;

- 📊 профилирование;

- 🔄 асинхронность;
- 🗄️ оптимизация запросов;

- 🧊 stateless-сервисы;

- 🧩 шардирование;

- 🔁 retry;

- ⏱️ таймауты;

- 📝 логирование.

### 5-5 Сопровождаемость

- 📖 читаемость;
- 🧪 тесты;
- 📄 документация;
- 🎨 единый стиль;
- 🏛️ понятная архитектура.

### 5-6 Тестируемость

- 🔗 слабая связанность;
- 💉 внедрение зависимостей;

- 🚧 изоляция побочных эффектов.

## 6 Антипаттерны

> Полезно знать не только хорошие принципы, но и типичные ошибки.

| Антипаттерн | Описание |
|---|---|
| 🐘 **God Object** | Класс, который знает и делает слишком много |
| 🍝 **Spaghetti Code** | Запутанный код без структуры |
| 📋 **Copy-Paste Programming** | Массовое дублирование |
| 🔨 **Golden Hammer** | Использование одного решения для всего |
| ⚡ **Premature Optimization** | Оптимизация без необходимости |
| 🏗️ **Overengineering** | Избыточное усложнение |
| 🌪️ **Big Ball of Mud** | Система без чёткой архитектуры |
| 🌋 **Lava Flow** | Мёртвый код, который боятся удалить |

## 8 Главная мысль

> 🎯 **Принципы разработки ПО — это инструменты, а не догма.**

Их цель:

- 📖 сделать код **понятным**;
- 🛡️ систему — **надёжной**;
- 💰 изменения — **дешёвыми**;
- 🚀 команду — **эффективной**.

**Лучшее решение — то, которое решает задачу сейчас и не мешает развивать систему завтра.**
