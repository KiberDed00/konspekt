# Конспект: Основные принципы разработки ПО

## 1. Введение

**Принципы разработки ПО** — это обобщённые правила и подходы, которые помогают создавать программы, которые легко:
- читать;
- тестировать;
- изменять;
- сопровождать;
- масштабировать.

**Главная цель** — управлять сложностью и снижать стоимость изменений.

---

## 2. Базовые принципы проектирования

### 2.1 Модульность
Разбиение системы на независимые части — модули.
- Каждый модуль решает свою задачу.
- Модули взаимодействуют через чёткие интерфейсы.
- Упрощает тестирование и замену компонентов.

### 2.2 Абстракция
Выделение существенных характеристик и скрытие деталей реализации.
- Позволяет работать на уровне интерфейсов, а не конкретных классов.
- Пример: `List` вместо `ArrayList`.

### 2.3 Инкапсуляция
Скрытие внутреннего состояния и деталей реализации.
- Доступ только через публичный интерфейс.
- Уменьшает связанность и риск ошибок.

### 2.4 Разделение ответственности — SoC
*Separation of Concerns* — каждая часть системы отвечает за свою задачу.
- UI, бизнес-логика и доступ к данным не должны смешиваться.

### 2.5 Слабая связанность и высокая связность
- **Слабая связанность** — минимум зависимостей между модулями.
- **Высокая связность** — элементы внутри модуля тесно связаны одной задачей.

### 2.6 Повторное использование
Код и решения должны переиспользоваться там, где это оправдано.
- Но без преждевременного обобщения.

## 3. Принципы написания кода

### 3.1 DRY — Don’t Repeat Yourself
Не дублируй знания и логику.
- Дублирование усложняет поддержку.
- Но не стоит объединять случайно похожий код.

### 3.2 KISS — Keep It Simple, Stupid
Простые решения предпочтительнее сложных.
- Чем проще код, тем легче его понять и изменить.

### 3.3 YAGNI — You Aren’t Gonna Need It
Не реализуй функциональность, которая может понадобиться в будущем.
- Сначала реальная потребность, потом реализация.

### 3.4 SOLID

| Принцип | Расшифровка | Суть |
|---|---|---|
| **S** | Single Responsibility | У класса одна причина для изменения |
| **O** | Open/Closed | Открыт для расширения, закрыт для изменения |
| **L** | Liskov Substitution | Наследник должен заменять родителя без поломки логики |
| **I** | Interface Segregation | Много специализированных интерфейсов лучше одного общего |
| **D** | Dependency Inversion | Зависимость от абстракций, а не от конкретных реализаций |

### 3.5 Композиция вместо наследования
Предпочитай собирать поведение из компонентов, а не строить глубокие иерархии наследования.

### 3.6 Закон Деметры
Объект должен знать как можно меньше о других объектах.
- Не вызывай цепочки вида `a.getB().getC().doSomething()`.

### 3.7 Fail Fast
Ошибка должна обнаруживаться как можно раньше.
- Проверяй входные данные.
- Не скрывай исключения без необходимости.

### 3.8 Защитное программирование
Код должен корректно реагировать на некорректные данные и неожиданные ситуации.
- Валидация.
- Обработка исключений.
- Понятные сообщения об ошибках.

### 3.9 Читаемость и единообразие
- Понятные имена.
- Единый стиль.
- Небольшие функции.
- Комментарии только там, где код неочевиден.

## 4. Процессные принципы

### 4.1 Итеративная разработка
Разработка короткими итерациями с обратной связью.
- Быстрее выявляются ошибки и меняются требования.

### 4.2 Agile-подходы
Scrum, Kanban и другие.
- Гибкость.
- Работа с обратной связью.
- Инкрементальная поставка ценности.

### 4.3 Версионирование
Использование Git и подобных систем.
- История изменений.
- Ветвление.
- Совместная работа.

### 4.4 Code Review
Проверка кода другими разработчиками.
- Повышает качество.
- Распространяет знания.
- Снижает количество ошибок.

### 4.5 Тестирование
- Модульные тесты.
- Интеграционные тесты.
- E2E-тесты.
- Регрессионное тестирование.

### 4.6 CI/CD
Непрерывная интеграция и доставка.
- Автоматическая сборка.
- Автотесты.
- Быстрый и безопасный релиз.

### 4.7 Рефакторинг
Улучшение структуры кода без изменения поведения.
- Борьба с техническим долгом.
- Повышение сопровождаемости.

### 4.8 Документация
- README.
- API-документация.
- Архитектурные решения — ADR.
- Комментарии только по делу.

### 4.9 Управление техническим долгом
Технический долг — это компромисс, который нужно контролировать.
- Фиксировать.
- Планировать возврат.
- Не допускать накопления.

---

## 5. Нефункциональные аспекты

- **Безопасность** — защита данных и доступов.
- **Производительность** — скорость и потребление ресурсов.
- **Масштабируемость** — рост нагрузки без переписывания.
- **Надёжность** — устойчивость к сбоям.
- **Сопровождаемость** — простота изменений.
- **Тестируемость** — возможность проверки поведения.

## 6. Краткий чек-лист

- [ ] Код понятен без длинных комментариев?
- [ ] Нет лишнего дублирования?
- [ ] Решение максимально простое?
- [ ] Нет преждевременной функциональности?
- [ ] Классы и модули имеют одну ответственность?
- [ ] Зависимости направлены на абстракции?
- [ ] Есть тесты?
- [ ] Изменения проходят review?
- [ ] Сборка и релиз автоматизированы?
- [ ] Технический долг под контролем?

---

## 7. Главная мысль

Принципы разработки ПО — это не догма, а инструменты.
Их цель — сделать код **понятным, надёжным и дешёвым в поддержке**.  
Лучшее решение — то, которое решает задачу сейчас и не мешает развивать систему завтра.
