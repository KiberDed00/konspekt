# Конспект: Основные принципы разработки ПО  
## Расширенная версия

> Принципы разработки ПО — это не жёсткие законы, а ориентиры, которые помогают управлять сложностью, снижать стоимость изменений и делать код понятным для команды.

---

## 0. Зачем вообще нужны принципы

Разработка ПО — это не только написание кода, который «работает сейчас». Важно, чтобы код:

- работал корректно;
- был понятен другим разработчикам;
- легко тестировался;
- легко изменялся;
- не ломался при добавлении новой функциональности;
- мог поддерживаться годами.

**Главная проблема** — сложность. Чем больше система, тем дороже каждое изменение. Принципы разработки помогают:

1. **Управлять сложностью** — разбивать систему на понятные части.
2. **Снижать стоимость изменений** — делать код гибким.
3. **Улучшать коммуникацию** — давать команде общий язык.
4. **Повышать качество** — уменьшать количество ошибок.
5. **Облегчать сопровождение** — чтобы новый разработчик мог быстро разобраться.

Принципы действуют на разных уровнях:

- проектирование архитектуры;
- написание кода;
- организация процесса;
- командная работа;
- эксплуатация и поддержка.

---

## 1. Базовые принципы проектирования

### 1.1 Модульность

**Модульность** — это разбиение системы на относительно независимые части — модули, каждый из которых выполняет свою задачу.

**Признаки хорошей модульности:**

- у модуля чёткая зона ответственности;
- модуль скрывает внутреннюю реализацию;
- взаимодействие происходит через понятный интерфейс;
- модуль можно заменить без переписывания всей системы.

**Пример:** интернет-магазин можно разделить на модули:

- каталог товаров;
- корзина;
- оформление заказа;
- оплата;
- доставка;
- уведомления.

**Плюсы:**

- проще тестировать;
- проще переиспользовать;
- проще распределять работу между командами;
- меньше вероятность, что изменение в одном месте сломает другое.

**Минусы:**

- нужно проектировать интерфейсы;
- появляется дополнительная сложность в интеграции;
- неверное разбиение может усложнить систему.

---

### 1.2 Абстракция

**Абстракция** — это выделение существенных характеристик объекта и скрытие несущественных деталей.

Абстракция позволяет работать не с конкретной реализацией, а с общим понятием.

**Пример:**

- Вместо `ArrayList` используем интерфейс `List`.
- Вместо конкретного `MySQLUserRepository` — интерфейс `UserRepository`.

**Зачем это нужно:**

- уменьшается связанность;
- можно менять реализацию без изменения клиентского кода;
- упрощается тестирование — можно подставить mock-объект.

**Осторожно:** абстракция не должна быть «дырявой». Если для работы с абстракцией нужно знать детали реализации — это плохая абстракция.

---

### 1.3 Инкапсуляция

**Инкапсуляция** — это скрытие внутреннего состояния объекта и предоставление доступа к нему только через публичный интерфейс.

**Что даёт инкапсуляция:**

- защита инвариантов класса;
- контроль над изменениями состояния;
- уменьшение связанности;
- возможность менять внутреннюю реализацию.

**Пример:**

```java
class BankAccount {
    private Money balance;

    public void deposit(Money amount) {
        if (amount.isNegative()) {
            throw new IllegalArgumentException("Сумма должна быть положительной");
        }
        balance = balance.add(amount);
    }

    public Money getBalance() {
        return balance;
    }
}
```

Здесь нельзя напрямую изменить `balance` в обход проверок.

**Типичная ошибка:** делать все поля публичными или генерировать getters/setters для всего подряд. Это не инкапсуляция, а формальный доступ.

---

### 1.4 Разделение ответственности — Separation of Concerns, SoC

**SoC** — принцип, согласно которому система должна быть разделена на части, каждая из которых отвечает за свою задачу.

**Примеры:**

- UI не должен содержать бизнес-логику;
- бизнес-логика не должна знать, как устроена база данных;
- доступ к данным не должен заниматься форматированием ответа.

**Популярные проявления SoC:**

- MVC, MVP, MVVM;
- слоистая архитектура;
- Clean Architecture;
- Hexagonal Architecture;
- микросервисы.

**Главная идея:** каждая часть должна заниматься своим делом и как можно меньше знать о других.

---

### 1.5 Слабая связанность и высокая связность

Это два взаимодополняющих принципа.

**Слабая связанность — Low Coupling**

Модули должны как можно меньше зависеть друг от друга.

- Изменение в одном модуле не должно требовать изменений в десяти других.
- Взаимодействие — через интерфейсы, события, контракты.

**Высокая связность — High Cohesion**

Элементы внутри модуля должны быть тесно связаны одной задачей.

- Класс должен делать одну вещь.
- Модуль должен иметь чёткую цель.

**Идеал:** модули слабо связаны между собой, но внутри каждого модуля элементы сильно связаны.

---

### 1.6 Повторное использование

**Повторное использование** — это возможность применять существующие решения в новых контекстах.

Но здесь есть важное правило:

> Не обобщай раньше времени.

Если код совпадает случайно, его объединение может привести к плохой абстракции. Полезно использовать **правило трёх**:

1. Первый раз — просто пишем код.
2. Второй раз — терпим дублирование.
3. Третий раз — задумываемся об абстракции.

## 2. Принципы написания кода

### 2.1 DRY — Don’t Repeat Yourself

**DRY** — не повторяй себя. Каждое знание в системе должно иметь единственное представление.

**Что считается дублированием:**

- копипаста кода;
- дублирование бизнес-правил;
- дублирование конфигурации;
- дублирование структуры данных.

**Почему это плохо:**

- при изменении нужно править в нескольких местах;
- легко забыть одно из мест;
- растёт риск ошибок.

**Важно:** DRY не означает «объединить любой похожий код». Если два участка кода выглядят одинаково, но меняются по разным причинам — их не нужно объединять.

---

### 2.2 KISS — Keep It Simple, Stupid

**KISS** — делай проще. Простое решение обычно лучше сложного.

**Признаки простого кода:**

- легко читается;
- легко тестируется;
- содержит минимум абстракций;
- не требует долгого изучения.

**Что мешает простоте:**

- преждевременная оптимизация;
- избыточные паттерны;
- сложные иерархии наследования;
- «умный» код, который непонятен без комментариев.

---

### 2.3 YAGNI — You Aren’t Gonna Need It

**YAGNI** — не реализуй то, что может понадобиться в будущем.

**Проблема:** разработчики часто добавляют функциональность «на всякий случай». В итоге:

- код усложняется;
- появляются неиспользуемые ветки;
- увеличивается стоимость поддержки;
- сложнее менять систему.

**Правильный подход:** реализуем только то, что нужно сейчас. Если потребуется — добавим позже.

---

### 2.4 SOLID

SOLID — это пять принципов объектно-ориентированного проектирования.

| Принцип | Расшифровка | Суть |
|---|---|---|
| **S** | Single Responsibility Principle | У класса одна причина для изменения |
| **O** | Open/Closed Principle | Открыт для расширения, закрыт для изменения |
| **L** | Liskov Substitution Principle | Наследник должен заменять родителя без поломки логики |
| **I** | Interface Segregation Principle | Лучше много специализированных интерфейсов, чем один общий |
| **D** | Dependency Inversion Principle | Зависимость от абстракций, а не от конкретных реализаций |

#### S — Single Responsibility Principle

Класс должен иметь только одну причину для изменения.

**Плохо:**

```java
class Order {
    void calculateTotal() { ... }
    void saveToDatabase() { ... }
    void printInvoice() { ... }
}
```

**Хорошо:**

```java
class Order { ... }
class OrderRepository { ... }
class InvoicePrinter { ... }
```

---

#### O — Open/Closed Principle

Класс должен быть открыт для расширения, но закрыт для изменения.

**Плохо:**

```java
if (type == "card") { ... }
else if (type == "cash") { ... }
else if (type == "crypto") { ... }
```

**Хорошо:** использовать полиморфизм.

```java
interface PaymentMethod {
    void pay();
}

class CardPayment implements PaymentMethod { ... }
class CashPayment implements PaymentMethod { ... }
```

---

#### L — Liskov Substitution Principle

Объекты наследника должны заменять объекты родителя без нарушения корректности программы.

**Классический пример:** квадрат и прямоугольник. Если `Square` наследует `Rectangle`, но меняет поведение сеттеров, это нарушает LSP.

**Признак нарушения:**

- наследник выбрасывает исключение там, где родитель работает;
- наследник игнорирует часть поведения родителя;
- клиентский код вынужден проверять тип наследника.

---

#### I — Interface Segregation Principle

Клиенты не должны зависеть от методов, которые они не используют.

**Плохо:**

```java
interface Worker {
    void work();
    void eat();
    void sleep();
}
```

Роботу не нужно `eat()` и `sleep()`.

**Хорошо:**

```java
interface Workable { void work(); }
interface Eatable { void eat(); }
interface Sleepable { void sleep(); }
```

---

#### D — Dependency Inversion Principle

Модули верхнего уровня не должны зависеть от модулей нижнего уровня. Оба должны зависеть от абстракций.

**Плохо:**

```java
class OrderService {
    private MySQLOrderRepository repository = new MySQLOrderRepository();
}
```

**Хорошо:**

```java
class OrderService {
    private final OrderRepository repository;

    OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}
```

---

### 2.5 Композиция вместо наследования

Наследование создаёт жёсткую связь между классами. Композиция — более гибкий подход.

**Плохо:**

```java
class Car extends Engine { ... }
```

**Хорошо:**

```java
class Car {
    private Engine engine;
}
```

**Почему композиция лучше:**

- меньше связанность;
- проще менять поведение;
- нет проблем с хрупким базовым классом;
- можно комбинировать поведение.

---

### 2.6 Закон Деметры — Law of Demeter

Объект должен знать как можно меньше о других объектах.

**Плохо:**

```java
order.getCustomer().getAddress().getCity().getName();
```

**Хорошо:**

```java
order.getCustomerCity();
```

**Суть:** не вызывай методы у объектов, полученных через цепочку. Это уменьшает связанность.

---

### 2.7 Fail Fast

Ошибка должна обнаруживаться как можно раньше.

**Практики:**

- проверять входные данные;
- использовать assertions;
- выбрасывать исключения при некорректном состоянии;
- не скрывать ошибки.

**Пример:**

```java
public void setAge(int age) {
    if (age < 0) {
        throw new IllegalArgumentException("Возраст не может быть отрицательным");
    }
    this.age = age;
}
```

---

### 2.8 Защитное программирование

Код должен корректно реагировать на некорректные данные и неожиданные ситуации.

**Что сюда входит:**

- валидация входных данных;
- обработка исключений;
- проверка граничных условий;
- понятные сообщения об ошибках;
- логирование.

**Важно:** не путать с избыточной проверкой всего подряд. Проверять нужно там, где действительно может прийти некорректное значение.

---

### 2.9 Читаемость и единообразие

Код читается гораздо чаще, чем пишется.

**Принципы:**

- понятные имена переменных и методов;
- единый стиль форматирования;
- небольшие функции;
- минимум комментариев, но там, где нужно;
- отсутствие «магических чисел»;
- последовательность в структуре проекта.

**Пример плохого имени:**

```java
int d;
```

**Пример хорошего имени:**

```java
int daysUntilDeadline;
```

---

### 2.10 Принцип наименьшего удивления

Поведение кода должно быть предсказуемым.

- метод `save()` должен сохранять, а не удалять;
- `getBalance()` не должен менять баланс;
- названия должны соответствовать действию.

Код не должен удивлять того, кто его читает.

## 3. Процессные принципы

### 3.1 Итеративная разработка

Разработка идёт короткими итерациями.

**Плюсы:**

- быстрая обратная связь;
- можно раньше обнаружить ошибки;
- требования можно уточнять по ходу;
- снижается риск сделать не то.

**Пример:** MVP — минимально жизнеспособный продукт.

---

### 3.2 Agile-подходы

Agile — это набор ценностей и принципов.

**Основные идеи:**

- люди и взаимодействие важнее процессов и инструментов;
- работающий продукт важнее документации;
- сотрудничество с заказчиком важнее согласования контракта;
- готовность к изменениям важнее следования плану.

**Популярные фреймворки:**

- Scrum;
- Kanban;
- XP.

---

### 3.3 Версионирование

Использование систем контроля версий, чаще всего Git.

**Практики:**

- атомарные коммиты;
- понятные сообщения;
- ветвление;
- code review;
- pull request;
- trunk-based development или Git Flow.

**Семантическое версионирование:**

- `MAJOR` — несовместимые изменения;
- `MINOR` — новая функциональность;
- `PATCH` — исправления.

---

### 3.4 Code Review

Проверка кода другими разработчиками.

**Цели:**

- найти ошибки;
- улучшить качество;
- распространить знания;
- соблюсти стандарты;
- обсудить архитектурные решения.

**Хорошие практики:**

- небольшие PR;
- понятное описание;
- конструктивная обратная связь;
- автоматические проверки до review.

---

### 3.5 Тестирование

**Пирамида тестирования:**

1. Модульные тесты — много, быстрые.
2. Интеграционные тесты — меньше, медленнее.
3. E2E-тесты — мало, самые медленные.

**Виды тестов:**

- unit;
- integration;
- functional;
- regression;
- performance;
- security.

**TDD — Test-Driven Development:**

1. Пишем падающий тест.
2. Пишем минимальный код, чтобы тест прошёл.
3. Рефакторим.

---

### 3.6 CI/CD

**CI — Continuous Integration**  
Непрерывная интеграция: изменения часто сливаются в основную ветку и автоматически проверяются.

**CD — Continuous Delivery / Deployment**  
Непрерывная доставка или развёртывание.

**Типичный pipeline:**

1. Сборка.
2. Линтеры.
3. Тесты.
4. Сканирование безопасности.
5. Сборка артефакта.
6. Деплой на staging.
7. Деплой в production.

**Плюсы:**

- быстрая обратная связь;
- меньше ручных ошибок;
- предсказуемые релизы.

---

### 3.7 Рефакторинг

**Рефакторинг** — улучшение структуры кода без изменения его поведения.

**Когда нужен:**

- код трудно читать;
- появилось дублирование;
- методы слишком длинные;
- классы делают слишком много;
- перед добавлением новой функциональности.

**Важно:** рефакторинг должен быть безопасным. Лучше делать его под защитой тестов.

---

### 3.8 Документация

Документация должна быть полезной, а не формальной.

**Виды:**

- README — как запустить проект;
- API-документация;
- архитектурные решения — ADR;
- схемы;
- комментарии в коде.

**Правило:** комментарий должен объяснять «почему», а не «что». Если код понятен без комментария — комментарий не нужен.

---

### 3.9 Управление техническим долгом

**Технический долг** — это накопленные компромиссы, которые усложняют дальнейшую разработку.

**Примеры:**

- костыли;
- устаревшие библиотеки;
- отсутствие тестов;
- плохая архитектура;
- дублирование.

**Что делать:**

- фиксировать долг;
- оценивать его влияние;
- планировать погашение;
- не допускать бесконтрольного накопления.

**Квадранты технического долга:**

- осознанный и необходимый;
- осознанный и ненужный;
- неосознанный и необходимый;
- неосознанный и ненужный.

---

## 4. Архитектурные принципы

### 4.1 Разделение на слои

Типичные слои:

- представление;
- приложение;
- домен;
- инфраструктура.

**Правило зависимостей:** зависимости направлены внутрь, к домену. Домен не должен знать о базе данных, веб-фреймворке или UI.

---

### 4.2 Clean Architecture

Идея: бизнес-логика не зависит от фреймворков, БД, UI и внешних сервисов.

**Слои:**

- Entities;
- Use Cases;
- Interface Adapters;
- Frameworks & Drivers.

**Плюсы:**

- тестируемость;
- независимость от технологий;
- гибкость.

---

### 4.3 Hexagonal Architecture

Также известна как Ports and Adapters.

- Ядро приложения.
- Порты — интерфейсы.
- Адаптеры — реализации для БД, HTTP, очередей.

---

### 4.4 DDD — Domain-Driven Design

**Ключевые идеи:**

- единый язык — ubiquitous language;
- ограниченные контексты — bounded contexts;
- сущности;
- value objects;
- агрегаты;
- доменные события.

DDD помогает бороться со сложностью предметной области.

---

### 4.5 API-first и контракты

Сначала проектируем API, потом реализацию.

**Плюсы:**

- команды могут работать параллельно;
- контракт понятен заранее;
- меньше интеграционных проблем.

---

## 5. Нефункциональные аспекты

Принципы разработки касаются не только кода, но и качества системы.

### 5.1 Безопасность

- принцип наименьших привилегий;
- валидация входных данных;
- защита от OWASP Top 10;
- шифрование;
- управление секретами.

### 5.2 Производительность

- профилирование;
- кэширование;
- асинхронность;
- оптимизация запросов;
- избегание преждевременной оптимизации.

### 5.3 Масштабируемость

- горизонтальное масштабирование;
- stateless-сервисы;
- очереди;
- шардирование;
- балансировка нагрузки.

### 5.4 Надёжность

- обработка сбоев;
- retry;
- circuit breaker;
- таймауты;
- мониторинг;
- логирование.

### 5.5 Сопровождаемость

- читаемость;
- тесты;
- документация;
- единый стиль;
- понятная архитектура.

### 5.6 Тестируемость

- слабая связанность;
- внедрение зависимостей;
- чистые функции;
- изоляция побочных эффектов.

## 6. Антипаттерны

Полезно знать не только хорошие принципы, но и типичные ошибки.

| Антипаттерн | Описание |
|---|---|
| God Object | Класс, который знает и делает слишком много |
| Spaghetti Code | Запутанный код без структуры |
| Copy-Paste Programming | Массовое дублирование |
| Golden Hammer | Использование одного решения для всего |
| Premature Optimization | Оптимизация без необходимости |
| Overengineering | Избыточное усложнение |
| Big Ball of Mud | Система без чёткой архитектуры |
| Lava Flow | Мёртвый код, который боятся удалить |

## 7. Краткий чек-лист

- [ ] Код понятен без длинных комментариев?
- [ ] Нет лишнего дублирования?
- [ ] Решение максимально простое?
- [ ] Нет преждевременной функциональности?
- [ ] Классы и модули имеют одну ответственность?
- [ ] Зависимости направлены на абстракции?
- [ ] Композиция используется там, где наследование не оправдано?
- [ ] Ошибки обнаруживаются как можно раньше?
- [ ] Есть тесты?
- [ ] Изменения проходят code review?
- [ ] Сборка и релиз автоматизированы?
- [ ] Технический долг под контролем?
- [ ] Документация актуальна?
- [ ] Безопасность учтена?
- [ ] Производительность измеряется, а не угадывается?

---

## 8. Главная мысль

Принципы разработки ПО — это инструменты, а не догма.

Их цель:

- сделать код **понятным**;
- систему — **надёжной**;
- изменения — **дешёвыми**;
- команду — **эффективной**
